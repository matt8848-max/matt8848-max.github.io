# MySQL架构

数据库软件用于大量存储且带有一定更新的任务。

## 数据页
MySQL像excel那样按表组织数据结构。
防止大文件读写问题，MySQL会将数据拆成一个个数据页，每页默认16kb。

[存储的详细说明](./基础篇.md#存储记录的模式)

## 索引
为每个数据页加入**页号**，再为每行数据加个**序号**，这个**序号**其实就是所谓的主键。

将每个数据页里最小的主键序号和所在页的页号提出来，就可以按照B+树构建索引。
+ 针对主键的索引，就是**主键索引**
+ 其他数据表的列去建立索引，就是**辅助索引**

## Buffer Pool
由于磁盘太慢，Buffer Pool充当缓存。
绕开系统自带的缓存，是为了可以定制更多缓存策略，还能实现加锁等各种数据表高级特性。

> buffer Pool 通过[直接 I/O](../操作系统/网络系统.md#大文件传输方式) 模式

## 自适应hash索引

对于热点数据页，我们以查询的值为 key，数据页地址为 value，构建 hash 表。
这能提高查询速度。

## Change Buffer

更新完主键索引的数据页之后，还需要更新辅助索引页。这样读取辅助索引页的磁盘 I/O 必然少不了。

我们可以先将要写入的数据收集到一块内存里，等哪天磁盘里的索引页正好被读入 Buffer pool 的时候，再将写入数据应用到索引页中。
这样能减少不必要的I/O开销，提升性能。

将写操作收集起来的地方，就是所谓的 Change Buffer，它其实是 Buffer pool 的一部分。

Change Buffer 只适用于非唯一的二级索引。对于主键索引和唯一二级索引在更新时需要判断是否会产生唯一性冲突，就无法写延迟，也就用不上change buffer。

## Undo Log

此功能用于服务于表内数据的事务。（注意MySQL的事务功能并非完全符合SQL标准）

会用旧数据生成 undo log 记录，存储在 Buffer Pool 中的特殊 undo log 内存页中。
并随着 buffer pool 的刷盘机制，不定时写入到磁盘的 undo log 文件中。

## Redo Log

前文都是内存相关的设计。如果突然中断会丢失数据。

我们将事务中更新数据行的操作都写入到 redo log buffer 内存中，然后在事务提交的时候进行 redo log 刷磁盘，将数据固化到 redo log 文件中。

数据库进程崩溃重启后，就能通过 redo log file 找到历史操作记录，重做数据。保证要么都成功，要么都失败。

Redo Log是顺序写入的，比随机写的buffer pool会快很多。

> redo log 的作用并不是保证所有数据不丢失，而是确保已提交事务的变更不会丢失。
>
> redo log 本质上是写入性能和数据完整性折中的产物

## Innodb是什么

存储引擎。前文所述功能的提供者。

## Server 层是什么

Server 层，本质上是 sql 语句 和 innodb 存储引擎之间的中间层。
+ 连接管理模块：管理来自应用的网络连接
+ 分析器：判断 SQL 语句有没有语法错误
+ 优化器：根据一定的规则选择该用什么索引
+ 执行器：根据执行计划去调用Innodb 存储引擎的接口函数

server 层和存储引擎层是通过接口函数进行解耦的

## binlog 是什么

erver 层会将历史上所有变更操作记录到磁盘上的日志文件中，这个日志文件就是所谓的 binlog。

+ redo log 是环状写入的，后面写的内容最终会覆盖前面的内容
+ binlog 却会记录所有历史变更

## MySQL主从架构

利用binlog可以实现主从架构。
主数据库负责承接写流量，从数据库负责读流量。

它就是经典的 mysql 主从同步架构。

## 数据库查询更新流程


首先不管是查询还是更新操作，客户端都会先跟 mysql 建立网络连接，并将 sql 发送到 server 层，经过分析器解析 sql 语法、优化器选择索引生成执行计划，最终给到执行器调用 InnoDB 的函数接口。

+ 对于读操作。
    + InnoDB存储引擎会先检查 Buffer Pool 中是否存在所需的 B+树数据页，如果存在则直接返回数据。
    + 如果 Buffer Pool 中没有所需的数据页，则会从磁盘中读取相应的数据页加载到 Buffer Pool 中，再返回数据。
    + 同时，如果查询的数据是热点数据，还会将数据页加入到自适应哈希索引豪华套餐中，加速后续的查询。 
+ 对于写操作
    + 先将数据写入 Buffer Pool，并生成相应的 Undo Log 记录，以便在事务回滚时能够恢复数据的原始状态。
    + 接下来，会将写操作记录到 Redo Log Buffer 中，这些 redo log 会周期性地写入到磁盘中的 Redo Log 文件中，就算数据库崩了，已提交的事务也不会丢失。
    + 对于辅助索引的更新操作，InnoDB 会将这些更新暂时存储在 Change Buffer 中，等到相关的索引页被读取到 Buffer Pool 时再进行实际的更新操作，从而减少磁盘 I/O，提高写入性能。
    + 同时，所有的变更都会记录到 server 层的 binlog 中，以便进行数据恢复。
